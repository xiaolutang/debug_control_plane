## Implementation Scope

### 目标
在 Python `BridgeClient` 中增加 debug plane auth 的 token provider、Bearer header 注入、auth-specific error taxonomy 和 `/auth/request`、`/auth/status`、`/auth/claim` helper，使 Python 只携带凭证并消费 App debug plane 的稳定 401/403 协议，不改变 DevicePool 身份持久化。

### 范围内
- 在 `python/debug_control_plane/mcp_plane/bridge_client.py` 定义 `DebugAuthTokenProvider` Protocol，至少包含 `get_token(device_id) -> str | None`、`save_token(device_id, token, metadata)`、`clear_token(device_id, reason)`。
- `BridgeClient.__init__` 增加可选 `token_provider`，默认 `None` 保持现有裸用兼容。
- 抽出 `_auth_headers(device_id)` 或等价 helper：存在 token 时返回 `{"Authorization": "Bearer <token>"}`；token 缺失或 provider 为 `None` 时返回空 headers，不伪造授权、不抛本地授权成功。
- `invoke`、`read`、`hello`、`events` 均必须经过同一 token provider/header helper；`invoke` 的 `json=` 与 `content=` 两条分支都必须传入 headers；`events` 的 `Client.stream("GET", ...)` 必须传入 headers。
- 新增 `DeviceAuthError(DeviceHttpError)` 或等价 subclass，保留 `status_code`、`body`，并暴露稳定 `code` 字段；只在 App 返回 401/403 且 body 含 `{ok:false, code, message}` 或等价 dict code 时使用。
- 对 `401 token_expired`、`401 token_revoked`、`401 invalid_token` 调用 `token_provider.clear_token(device_id, reason=<code>)`；`authorization_required` 不清有效 token，403 `authorization_denied`/`forbidden` 不自动清 token。
- 增加 `/auth/request`、`/auth/status`、`/auth/claim` helper，使用 `POST` JSON object body，对齐 `PROTOCOL.md` §2.3；`claim` 成功返回 token 时调用 `save_token(device_id, token, metadata)`，metadata 至少保留 `tokenId`、`expiresAt` 中存在的字段。
- 扩展 `python/tests/test_bridge_client.py`，使用 `httpx.MockTransport` 和 fake token provider 覆盖 header 注入、缺 token、auth error code 解析、clear/save 行为和 auth bootstrap helpers。
- 写入必要 evidence：focused pytest 和 all Python tests 的命令、退出码、passed 数、关键测试名。

### 范围外
- 不修改 `python/debug_control_plane/device_discovery/device_pool.py`。
- 不修改 `DevicePool` 持久化 schema，不把 token 写入 `devices.json`，不让 DevicePool 负责 auth token 生命周期。
- 不修改 `python/debug_control_plane/mcp_plane/server.py`、`capability_mirror.py` 或 MCP tool error surfacing；这些属于后续 R001-BB001。
- 不修改 Kotlin、Dart、Flutter、fixtures 或 `PROTOCOL.md`。
- 不实现 OAuth、JWT、RBAC/scope、多用户权限、refresh token、完整 MCP Streamable HTTP server 或 App 侧最终授权判定。
- 不通过 query string、URL path、request body、cookie、SSE event data、`appMeta` 或 `/hello` 聚合 state 传递 token。
- 不记录、打印或在异常 message 中暴露明文 token。

### 已知约束
- `PROTOCOL.md` §2.2 规定敏感请求只能使用 `Authorization: Bearer <opaque-token>` header；`/state`、`/events`、capability GET/POST 均为敏感端点。
- `GET /hello` 和 `/auth/*` bootstrap 端点可未授权访问；`hello` 仍应使用 token provider 尝试注入 Bearer header，以便授权后获取完整 capability mirror。
- `PROTOCOL.md` §2.4 的 auth failures 使用 `{ok:false, code, message}`，稳定 code 包括 `authorization_required`、`invalid_token`、`token_expired`、`token_revoked`、`authorization_denied`、`forbidden`。
- Python 侧不能自行判定 token 是否最终有效；App debug plane 是真实资源边界。
- `DevicePool` 是 identity-only store；auth token provider/store 必须是 BridgeClient 的独立可选依赖或调用方注入实现。

### 任务流程图
1. one-shot request:
   - caller 调用 `invoke/read/hello`。
   - `BridgeClient.resolve(device_id)` 每次解析 fresh host。
   - `_auth_headers(device_id)` 读取 token；有 token 注入 Bearer header，无 token 使用空 headers。
   - httpx 发出 request/get；响应 2xx 按现有 `_safe_body`/`NetworkTarget.from_hello` 路径处理。
   - 响应 401/403 且含 stable auth `code` 时抛 `DeviceAuthError`；expired/revoked/invalid 清 token。

2. SSE request:
   - caller 迭代 `events(device_id)`。
   - 建连前 resolve host 并注入同一 auth headers。
   - stream response status >= 400 时先 `resp.read()`，解析 body，按 auth code 抛 `DeviceAuthError` 或保持 `DeviceHttpError`。
   - 授权成功后 `_iter_sse`、`DebugEvent.from_json`、`event_types` filter 行为不变。

3. auth bootstrap helpers:
   - `auth_request(device_id, client_nonce, client_label?, requested_method?, requested_path?)` -> `POST /auth/request`。
   - `auth_status(device_id, request_id, client_nonce)` -> `POST /auth/status`。
   - `auth_claim(device_id, request_id, client_nonce)` -> `POST /auth/claim`；成功 body 中 `token` 存在时通过 provider 保存 token，并返回 App 原始 response body。

### 评估者挑战记录
- Q: 是否允许把 token 存进 DevicePool 以复用已有 `devices.json`？
  A: 不允许。任务 blocked_files 明确禁止 `device_pool.py`，分析和设计均声明 DevicePool 是 identity-only store。
  Conclusion: token provider 必须独立于 DevicePool 持久化 schema。
- Q: token 缺失时是否应在 Python 本地直接抛授权错误？
  A: R001-BF009 的职责是携带凭证并消费 App 返回的标准 401；无 token 时不伪造授权，让 App debug plane 返回 `authorization_required`。
  Conclusion: 缺 token 发送无 Authorization header 的请求，除 transport/resolve 失败外不本地短路。
- Q: `/auth/*` helper 是否意味着实现 OAuth/JWT/RBAC 或 MCP HTTP server？
  A: 不意味着。helper 只按 `PROTOCOL.md` §2.3 调用 App bootstrap endpoints 并保存 claim 返回的 opaque token。
  Conclusion: OAuth/JWT/RBAC/full MCP HTTP server 全部在范围外。
