## Implementation Scope

### 目标
让 McpServer 把 App debug plane 的 401/403 鉴权错误（`DeviceAuthError`）翻译成稳定、可操作的 MCP isError 结果（授权 / 重新授权 / 权限不足三类提示），并让 `list_capabilities` / `subscribe_events` 不把 auth error 静默降级为"无能力/崩溃"。

### 范围内
- BB001.1 `server.py::_bridge_error_to_mcp` 增加 `DeviceAuthError` 分支（置于 `DeviceHttpError` 分支之前，利用 isinstance 顺序），按稳定 `code` 输出可操作提示：
  - `authorization_required` → 提示去 App 授权（授权请求/等待用户同意），不提示"token 校验失败"。
  - `token_expired` / `token_revoked` / `invalid_token` → 提示本地缓存 token 已被清理（BF009 已在 BridgeClient 层清理），需在 App 重新授权。
  - `authorization_denied` / `forbidden` → 提示当前授权不足/被 App 拒绝，不要自动重试。
  - message 中包含 device_id 与原始 code；不包含明文 token。
- BB001.2 `capability_mirror.py::refresh` 区分 auth error：`DeviceAuthError` 不与 offline/stale 同等静默 degrade——引入可查询的 per-device auth 状态（如 `auth_error(device_id)` 或 refresh 返回结构化信号），使 `h_list_capabilities` 对 auth error 抛出 MCP isError（穿透），而非返回空 schema 列表。offline/stale/普通 HTTP 错误维持现有 degrade-only 行为不变。
- `server.py::h_list_capabilities`：probe 中捕获 `DeviceAuthError`（Mirror 不再吞掉），转 `_bridge_error_to_mcp` 抛出 MCP error。
- BB001.3 `server.py::h_subscribe_events`：建连 401/403（含 `DeviceAuthError`）映射为 MCP isError，不崩溃、不静默返回空事件列表；既有 transport/unreachable 行为不变。
- 测试：扩展 `python/tests/test_server.py`（auth error message 映射、list_capabilities / subscribe_events / get_state auth 路径）与 `python/tests/test_capability_mirror.py`（refresh auth error 不静默清缓存语义）。

### 范围外
- 不修改 `bridge_client.py`（BF009 已交付 `DeviceAuthError`、token provider、`/auth/*` helper）；不修改 `DevicePool`。
- 不实现 Python 本地 token 校验、OAuth/JWT/RBAC、refresh token、自动重试/自动重新授权流程。
- 不新增 MCP tool（如独立的 `request_authorization` tool）——auth bootstrap helper 已在 BF009 提供，本任务只做 error surfacing。
- 不修改 Kotlin/Dart/Flutter 侧代码与 `PROTOCOL.md`。
- 不改动 SSE 流中途 token 过期的主动断开（E4 第一版不要求）。
- `/hello` 未授权 2xx bootstrap 的 auth 字段解析（H3）不在本任务——本任务只处理 401/403 错误路径。

### 已知约束
- `DeviceAuthError` 是 `DeviceHttpError` 子类；`_bridge_error_to_mcp` 分支顺序必须 auth 在前。
- `_AUTH_ERROR_CODES` 六个稳定 code 见 `bridge_client.py`；token 清理副作用已在 BF009 完成，MCP 层不得重复清理。
- `CapabilityMirror.refresh` 是 poll 安全的 degrade-only API（`_maybe_emit_list_changed_*` 依赖其不抛异常）；引入 auth 状态时不得破坏该不变量——对 poll 调用方 refresh 仍不抛异常，auth 信号必须可查询而非以异常穿透 refresh 本身。
- MCP error code 沿用 `-32602` 语义（用户可纠正错误），与既有翻译一致。
- token 明文不得出现在 message/日志。

### 任务流程图
1. auth error 翻译（BB001.1）:
   - tool handler（get_state/read_resource/invoke_command）→ `_run` catch → `_bridge_error_to_mcp(DeviceAuthError)` → 按 code 分支 → MCP isError，含去 App 授权/重新授权/权限不足提示。
2. list_capabilities（BB001.2）:
   - `h_list_capabilities` → `mirror.refresh(device_id)` → BridgeClient.hello 401/403 `DeviceAuthError` → Mirror 记录 per-device auth 状态（不静默当 degrade 清缓存误导为 offline）→ `h_list_capabilities` 检测 auth 状态 → 抛 MCP isError（含 code + 下一步提示）。
   - offline/stale/普通 HTTP 错误 → 维持现有 degrade（清缓存、返回 static/空列表）。
   - poll 调用方（`_maybe_emit_list_changed_*`）→ refresh 仍不抛异常，行为不变。
3. subscribe_events（BB001.3）:
   - `h_subscribe_events` → `client.events()` 建连 401/403 → `DeviceAuthError` 从 generator 抛出（在 to_thread 中迭代时触发）→ catch → `_bridge_error_to_mcp` → MCP isError，不崩溃。

### 评估者挑战记录
- Q: `list_capabilities` 用"auth error 穿透为 MCP error"还是"返回结构化 `{authorized:false,...}`"？
  A: 分析文档推荐前者（行为更清楚）；但 refresh 被 poll 调用方依赖"不抛异常"不变量，故采用混合：refresh 内部记录 auth 状态仍不抛异常，`h_list_capabilities` 主动检查并抛 MCP error。
  Conclusion: 穿透发生在 server handler 层，Mirror 保持 poll 安全。
- Q: auth error 时 CapabilityMirror 是否清空既有 schema 缓存？
  A: 不清。auth error ≠ 设备离线；保留缓存，授权恢复后无需重新拉取也正确（refresh 成功会重建）。但 auth 状态必须可查询，避免"看起来没能力"。
  Conclusion: auth error 分支不清缓存、不返回 had-cache 变更信号。
- Q: 是否需要新增 MCP tool 引导授权？
  A: 不需要。BF009 已有 `auth_request/status/claim` helper；本任务的 message 提示中可指向"在 App 上完成授权"即可，业务装配归后续任务。
  Conclusion: 不新增 tool，范围保持 error surfacing。
