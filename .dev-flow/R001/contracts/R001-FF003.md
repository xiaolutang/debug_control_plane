# Sprint Contract: R001-FF003

## Implementation Scope

Wire the Android Flutter plugin to the existing R001 auth core and the FF001/FF002
channel API. The native side must create an app-side auth manager, forward
pending authorization requests to Dart with `auth.request`, and handle Dart
approve/deny/revoke/status calls against that native manager.

In scope:
- Add auth method dispatch in `DebugControlPlaneFlutterPlugin.onMethodCall` for `auth.approve`, `auth.deny`, `auth.revoke`, and `auth.status`.
- Add native auth pending bridge support in `NativeControlPlaneBridge`, separate from capability invoke/state pending maps and timeouts.
- Add a native `DebugAuthManager` adapter used by the plugin-mounted `ControlPlane`.
- Add a small Android-side token store default, or an injectable interface with a default implementation, that persists token records across Flutter engine detach/reattach.
- Ensure auth enablement is explicit and local to the plugin/host bridge; no auth manager means the Kotlin core still uses its existing no-op behavior.
- Add Android unit tests under `flutter_debug_control_plane/android/src/test/kotlin/com/pantas/debug/controlplane/flutter/`.

Out of scope:
- No default Flutter UI, Android dialog, screen, notification, widget, or visual styling.
- No OAuth, JWT, RBAC, refresh token, scope model, user account system, TLS, or full MCP server.
- No Python changes and no `DevicePool` token persistence changes.
- No Dart API redesign beyond consuming the FF002 method names/payloads.
- No `PROTOCOL.md`, fixtures, Kotlin core route/auth semantics, or HTTP/SSE auth behavior changes beyond plugin adapter integration.
- No business package imports.

## Required API Shape

Native bridge:
- Add a native -> Dart pending auth method, for example `suspend fun requestAuthorization(req: DebugAuthPendingRequest, details: Map<String, Any?> = emptyMap())`.
- It must invoke `ChannelProtocol.AUTH_REQUEST` / `auth.request` with at least `requestId`, optional `pairingCode`, `status`, `expiresAt`, `clientLabel`, `method`, `endpoint`, and a native `reqId` only if needed for traceability.
- It must not store auth requests in `pending` or use `OwnedDeferred`, because those are capability reverse invoke waiters with the 30s route timeout.
- If the channel is detached, closed, throws, or returns not implemented, the auth manager must keep its pending/status/token store consistent and must not crash the app process.

Native auth manager adapter:
- Implement or compose a plugin-local class implementing `com.pantas.debug.controlplane.DebugAuthManager`.
- `requestAuthorization(body)` creates or reuses a pending request from `clientNonce`, `clientLabel`, `requestedMethod`, and `requestedPath`, forwards the pending signal to Dart, and returns a `DebugAuthRouteResult.Ok` payload compatible with `/auth/request`.
- `authorizationStatus(body)` reports pending/approved/denied/expired status for
  `requestId` and `clientNonce` without returning token plaintext.
- `claimAuthorization(body)` returns token/tokenId/expiresAt only for approved,
  unclaimed, non-expired requests and enforces one-time claim semantics.
- `authorize(request)` validates `Authorization: Bearer` tokens via core
  `DebugAuth.validateToken` or equivalent existing helpers.
- `helloAuthState(token)` returns stable auth bootstrap/status fields without
  leaking token plaintext.

Dart -> native dispatcher:
- `auth.approve` requires `requestId`, accepts optional `ttlSeconds` and `clientLabel`, marks the pending request approved, persists token hash/metadata, and returns a codec-safe map or `null` compatible with FF002 `DebugAuthClaim`.
- `auth.deny` requires `requestId`, accepts optional `reason`, marks the request
  denied, and returns `null`.
- `auth.revoke` accepts `tokenId` or `all=true`, marks persisted token records
  revoked without deleting unrelated state, and returns `null`.
- `auth.status` accepts optional `requestId` and returns a codec-safe status map.
- Invalid/missing arguments return stable `result.error("invalid_request", ...)`
  rather than throwing out of `onMethodCall`.

Token store:
- Persist only `DebugAuthTokenRecord` metadata and token hashes; never persist
  plaintext token values.
- Keep state outside the Flutter engine instance so engine detach does not drop
  persisted token records.
- Tests may use an in-memory fake store, but production must have a default or
  injectable Android store path usable by the plugin.

## Flow Requirements

Authorization request:
- Python calls `POST /auth/request`; `ControlPlane` delegates to the plugin-local
  `DebugAuthManager`.
- Manager creates/reuses pending state and asks `NativeControlPlaneBridge` to
  invoke Dart `auth.request`.
- HTTP returns pending payload with `requestId`, optional `pairingCode`, `status`,
  and `expiresAt` even if Dart has no UI handler attached.

Approve/claim:
- Dart calls `auth.approve`; plugin validates args and asks manager to approve,
  generate token plaintext once, and persist only hash/metadata.
- Python claims through `POST /auth/claim`; manager returns token only for
  approved, matching nonce, unexpired, unclaimed requests.
- Denied/expired/repeated claim paths return stable denied results.

Detach safety:
- Engine detach clears channel/plugin references but must not clear persisted
  token records.
- Late pending forwarding or auth status transitions must complete as no-op or
  stable error, not an uncaught exception.

## Acceptance Criteria

1. Native plugin forwards pending auth signals to Dart using `auth.request`.
2. `auth.request` pending handling is independent from capability invoke/state
   pending maps, fill-in methods, and 30s capability timeout behavior.
3. `auth.approve` updates the native auth manager, creates an approved request
   state, persists token hash/metadata, and returns a FF002-compatible result.
4. `auth.deny` updates the native auth manager to denied and future status/claim
   calls reflect denial.
5. `auth.revoke` revokes one token by `tokenId` or all tokens by `all=true`;
   subsequent `authorize` calls reject revoked tokens.
6. `auth.status` returns stable status maps for pending/approved/denied/expired
   requests and does not include token plaintext.
7. `claimAuthorization` supports one-time token claim after approval and rejects
   repeat, denied, expired, missing, or nonce-mismatched claims.
8. Engine detach or missing channel does not crash pending auth forwarding or
   auth method calls; persisted token state is not lost.
9. Existing plane lifecycle, capability register/unregister, events, state pull,
   reverse invoke, and ownership behavior continue to pass.
10. No default UI, OAuth/JWT/RBAC/full MCP server, Python changes, or Kotlin core
    auth semantic changes are introduced.

## Test Expectations

Required Android unit scenarios:
- `NativeControlPlaneBridge` invokes `ChannelProtocol.AUTH_REQUEST` with
  codec-safe args and does not add auth entries to capability `pending`.
- Auth request forwarding tolerates channel error/not implemented/detach without
  uncaught exceptions and without corrupting auth manager state.
- Plugin dispatcher routes `auth.approve`, `auth.deny`, `auth.revoke`, and
  `auth.status` to the native auth manager and validates required arguments.
- Approve/status/claim lifecycle covers pending -> approved -> one-time claim.
- Deny/status/claim lifecycle covers pending -> denied -> 403-style denied.
- Revoke lifecycle covers single-token and all-token revocation.
- Token persistence test proves stored records contain token hash/metadata, not
  plaintext token, and survive simulated engine detach/reattach or manager
  recreation with the same store.
- Existing FF001/FF002 Android plugin tests still pass.

Evidence command:

  `flutter_debug_control_plane/android/src/test/kotlin/...`.

  substitution if Gradle wrapper availability differs.
