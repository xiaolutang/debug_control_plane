## Implementation Summary

严格按契约 `.dev-flow/R003/contracts/R003-FF002.md`（status: agreed，KD-1~KD-5）实现：

1. **KD-1（scoped registry key，三方同构）**：`DartCapabilityRegistry.caps` 升级为 `LinkedHashMap<BridgeCapabilityIdentity, BridgeCapability>`；`BridgeCapabilityIdentity(type: CapabilityScopeType, pageId: String?, capId: String)` 仅三字段参与等值/哈希（data class），完整 `CapabilityScope`（含 pageName/revision）作为注册元数据存于 `BridgeCapability.scope`——pageName 不入 key 由结构保证。app key = `(app, null, id)`、page key = `(page, pageId, id)`，与 FF001 `_ScopedCapabilityKey` / BF005 `ScopedCapabilityKey` 逐字段同构。duplicate 按 scoped key 判定抛 IAE。`registeredIds` 保持 legacy app-only 视图。
2. **KD-2（parseDecl 缺省语义 + 拒绝规则）**：`parseScope(call)` 解析 `scope`（缺省 app；未知 wire 值经 `CapabilityScopeType.fromWire` 抛 IAE → `invalid_request`）；`scope=page` 且 pageId 缺失/空白 → IAE → `invalid_request`；`pageName` 可选仅元数据透传（不入 key）。`BridgeCapability` override `val scope`，使 `plane.register(cap)` 经 `ScopedCapabilityKey.from(cap.scope, cap.id)` 派生正确 key（BF005 语义消费）。
3. **KD-3（unregister/events.emit scope 透传）**：`CAPABILITY_UNREGISTER` 读 `scope?/pageId?`（缺省 app-only）→ `registry.remove(scope, capId)` + `plane.unregisterScoped(cap.scope, cap.id)` + `bridge.teardownCapability(identity)`；目标 key 不存在 → no-op success。`EVENTS_EMIT` 显式携带 scope/pageId 时按 scoped key 找 flow；缺省时 `resolveEmitTarget` 按 capId 以 app 条目优先、回退首个已注册 key（与 FF001 `_scopeFor` 同构）；未注册 scoped key → `not_started` 且不产生 flow 条目（M3 保持）。
4. **KD-4（eventFlows/teardown/reverse invoke 的 key 升级，契约登记 deviation）**：`NativeControlPlaneBridge.eventFlows` → `ConcurrentHashMap<BridgeCapabilityIdentity, MutableSharedFlow<DebugEvent>>`；`eventFlow`/`registeredEventFlow`/`teardownCapability`/`invokeHandler`/`pullState` 全部签名统一携带 scoped identity；`teardownCapability(identity)` 只移除该 key 的 event flow、只 fail 该 capability 自己的 pending invokes（`OwnedDeferred.owner` 为全 identity 过滤，同 capId 其它 key 不误杀）；`invokeHandler` 与 `pullState` 发出的 reverse invoke payload 均附 `scope`（wire 值 `app`/`page`，page 时加 `pageId`）。
5. **KD-5（BF005 遗留测试修复）**：见下文专门小节。
