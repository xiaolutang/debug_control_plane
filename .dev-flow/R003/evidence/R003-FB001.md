# R003-FB001 Evidence

## Implementation Summary

契约 KD-1~KD-5 全部落地：

- **KD-1 API 形态**：`PageCapabilityScope({required bridge, required pageId, String? pageName})`——pageId 空白在构造期经 `CapabilityScope.page()` 工厂抛 `ArgumentError`（零 channel）；pageName 仅展示元数据透传，不参与 key/唯一性。
- **KD-2 两段式**：
  - 预检查段（零 channel）：① dispose 终态 → `StateError`；② 输入列表内部 capId 重复（Set 收集检测）→ `StateError`；③ 与本页已注册 capId 冲突 → `StateError`；④ 本页已注册 capId 序列与输入序列逐位 deep 相同 → 幂等 no-op 返回，channel 零消息。
  - 发送段：预检查通过后逐个 `await bridge.register(cap, scope: _scope)`。bridge 失败包装 `StateError`，错误信息列出失败前已成功注册的 capId 清单；不做 undo，本页 `_registeredCapIds` 只 append 实际成功的成员（列表与实际注册一致）。
- **KD-3 显式 scope**：`_scope = CapabilityScope.page(...)` 构造一次复用；register 与 dispose 的 unregister 均**显式传 scope**，绝不走 app-only 缺省（规避 FF001 evaluate finding 的 `_scopeFor` app-first 歧义）。
- **KD-4 库导出**：`flutter_debug_control_plane.dart` 新增 `export 'src/page_capability_scope.dart';` + library doc 追加 helper 条目。
- **KD-5 状态层 owner 责任**：register payload 带 `scope=page/pageId/pageName?`、eager state push 带同一 page identity、dispose 逐个 `{capId, scope=page, pageId}`——均由单测逐字段断言；`registeredCount` / `isDisposed` / `pageId` getter 作为 FB002 控件数据来源交付。
