## Implementation Scope

### Goal

提供 Flutter 业务侧页面级 capability 生命周期注册器 `PageCapabilityScope`：业务以 pageId/pageName 构造，`registerAll` 把本页 capability 以显式 page scope 注册进 `NativeControlPlaneBridge`，`dispose` 按本 page scope 逐个 unregister——业务接入不手拼 MethodChannel payload（design §「页面生命周期」时序）。

### 关键决策

- **KD-1 API 形态**：`PageCapabilityScope({required NativeControlPlaneBridge bridge, required String pageId, String? pageName})`——pageId/pageName 在构造期传入并校验（pageId 非空白字符串，空则 `ArgumentError`；内部经 `CapabilityScope.page()` 工厂构造 scope，复用 BF002 已交付的校验与不变量）。pageName 仅展示元数据透传，不参与任何 key/唯一性（与 BF005 Selector Semantics 一致）。核心方法：`Future<void> registerAll(List<BridgeCapability> capabilities)`、`Future<void> dispose()`。
- **KD-2 同 scope 内 capId 去重与幂等（两段式，Round 1 Q1/Q2 修订采纳方案 A）**：
  - **预检查段（零 channel 消息）**：`registerAll` 先做全量预检查——① 输入列表内部去重检查（列表内出现重复 capId → `StateError`）；② 与本 helper 自身已注册 capId 列表比对（重复 → `StateError`）；③ 终态检查（dispose 后调用 → `StateError`）。预检查段任一失败都在发出任何 channel 消息**之前**抛出，channel 零消息、无副作用。
  - **「同列表」判定基准（Round 1 Q2）**：对 capId 序列做有序 deep 比较——预检查通过且输入列表的 capId 序列与本页已注册 capId 序列逐位相同即视为同列表，幂等重放 no-op（channel 零消息）；capId 序列不同（含新增/换序）→ `StateError`（页面生命周期内不支持增量注册，语义简单可预期，FB002 example 按 open 时构造一次使用）。该判定同步进单测断言。
  - **发送段（逐个 await，不承诺原子性）**：预检查通过后逐个 `bridge.register(...)`。bridge 侧失败如实接受部分注册：捕获后包装 `StateError`，错误信息列出本页**已成功注册**的 capId 清单，供业务定位与诊断；helper 不做回滚 undo（bridge 无批量撤销原语），但本页 capId 列表与实际注册保持一致（failed 之前成功的成员仍在列）。单线程 Flutter 业务正常路径下 bridge.register 不失败（其唯一失败源是同 key 重复注册，已被预检查拦截），此为并发等异常路径的防御性兜底而非常规承诺。
  - `dispose()` 幂等：第二次 dispose 是 no-op 且不发 channel 消息；dispose 后调用 `registerAll` → `StateError`（scope 已终结，不允许复活）。
- **KD-3 显式 scope 传递，不走缺省推导**：helper 注册时直接调 `bridge.register(cap, scope: CapabilityScope.page(pageId: ..., pageName: ...))`、dispose 逐个 `bridge.unregister(capId, scope: _scope)`——**显式传 scope，绝不依赖 `unregister(id)` 的 app-only 缺省**，也规避 `_scopeFor` 的 app-first 歧义（FF001 evaluate finding：缺省推导在 app/page 同 capId 共存时会命中 app 条目）。多 pageId 并存互不影响：A 页 dispose 只删 `(page, A, id)` key，`(page, B, id)` 与 `(app, id)` 不动。helper 同时维护本页已注册 capId 列表（注册成功逐个 append，dispose 清理后清空）作为状态源。
- **KD-4 库导出**：`flutter_debug_control_plane.dart` 新增 `export 'src/page_capability_scope.dart';`——公开 `PageCapabilityScope` 与其异常路径用到的既有类型；不新增导出 FF001 的 `_ScopedCapabilityKey` 等私有类型（本来就不可导出）。library doc comment 追加 helper 条目。
- **KD-5 稳定标识 owner 责任分解**：AcceptanceSpec 中 owners 含 FB001 的项共 6 个，本任务（无自有 UI 表面）按层拆分责任：

### 任务流程图

```text
正常路径:
  Widget Page → PageCapabilityScope(bridge, pageId, pageName)
    pageId 空/空白 → ArgumentError（零 channel）
  registerAll(caps)
    已 dispose → StateError（零 channel）
    已注册 capId 序列 deep 相同（同列表重放）→ no-op（零 channel）
    序列不同(含新增/换序)/列表内重复/已注册冲突 → StateError（零 channel，预检查段）
    否则逐个 bridge.register(cap, scope: CapabilityScope.page(pageId, pageName))
      [发送段失败: 如实接受部分注册, 错误信息列出已注册 capId]
      → capability.register {capId, resources, commands, scope:'page', pageId, pageName?}
      → 记入本页 capId 列表; eager state.update 带 page identity
  dispose()
    二次调用 → no-op（零 channel）
    否则逐个 bridge.unregister(capId, scope: _scope)
      → capability.unregister {capId, scope:'page', pageId}
      → 清空列表 → isDisposed = true
异常边界: 其它 page/app capability 永不被触碰（KD-3）
```

### 评估者挑战记录

- **Q1（KD-2，实质）**：质疑「同列表重放幂等」与「一失败即整体失败零消息」在 bridge 逐个 await 语义下自相矛盾——c2 失败时 c1 已发 channel 消息且已入 `_caps`。→ **采纳**：KD-2 改写为两段式方案 A——预检查段（列表内去重/与已注册冲突/终态）失败零 channel；发送段 bridge 失败如实接受部分注册、错误信息列出已注册 capId、不做 undo；删除「零消息 + 整体失败 + 无半成品」三连承诺。
- **Q2（KD-2 判定基准）**：质疑「列表相同」未定义 identical vs deep equality（BridgeCapability 无 value equality）。→ **采纳**：定义为本页已注册 capId 序列的有序 deep 比较，逐位相同即同列表，同步进单测断言。
- **Q3（流程字段）**：指出 `negotiation_rounds: 1` 与 Round 0「等待 Round 1」的记录不一致。→ **采纳**：status 转 agreed 时更新为实际收敛轮次 2。
