## Implementation Scope

### Goal

Implement Kotlin control plane scope-aware registry, selector dispatch, lifecycle cleanup, and app-only state aggregation so Android native core behavior matches the R003 protocol and Dart reference behavior.

### In Scope

- Modify `kotlin/src/main/kotlin/com/pantas/debug/controlplane/ControlPlane.kt`.
- Update Kotlin tests in `ControlPlaneTest.kt` and `SseAndRoutingIntegrationTest.kt`; update `Fakes.kt` only if needed for test setup.
- Add an internal `ScopedCapabilityKey(scope,pageId?,capabilityId)` where app key is `(APP,null,id)` and page key is `(PAGE,pageId,id)`.
- Use the same scoped key for capability registry and event subscription registry.
- Preserve `register(cap)` signature while deriving the key from `cap.scope`.
- Allow app/page same `id` and same `id` under multiple `pageId` values.
- Reject duplicate scoped key registration with `IllegalArgumentException` and keep the existing handler active.
- Preserve legacy `unregister(id)` as app-scope removal only.
- Add scoped unregister API that precisely removes one scoped entry and treats missing entries as no-op.
- Cancel the matching event subscription on app unregister, scoped unregister, duplicate-safe cleanup, and `stop()`.
- Broadcast `capability_scope_changed` after successful visible registry changes with payload fields `change`, `scope`, `capabilityId`, optional `pageId`, optional `pageName`, and `scopeRevision`.
- Maintain a monotonic registry revision. Each entry gets the revision assigned when it enters the current registry mirror; unrelated entries keep their previous revision.
- `/hello.registeredCapabilities[]` preserves `id/resources/commands/description?` shape and registration order, and adds scope metadata: app emits `scope=app` and `scopeRevision`; page emits `scope=page`, `pageId`, optional `pageName`, and `scopeRevision`.
- `/state` and `/hello` top-level state aggregate app-scope capabilities only.
- Capability dispatch supports selector headers `X-DCP-Capability-Id`, `X-DCP-Capability-Scope`, `X-DCP-Page-Id`, and `X-DCP-Scope-Revision`.
- Capability routes must perform auth before selector lookup, gone checks, revision checks, or path matching.
- A complete selector routes only within the selected capability resources/commands.
- No selector keeps legacy flat dispatch, using registration order first-match-wins.
- Selector page missing returns `410 page_capability_gone`.
- Selector revision mismatch returns `409 capability_scope_expired`.
- Selector target exists but method/path do not match returns existing `404 not_found`.

### Out Of Scope

- No Flutter, Dart, Python, fixture, or `PROTOCOL.md` changes.
- No `protocolVersion` change.
- Do not put `pageId/pageName` into capability ids, route paths, or MCP tool names.
- Do not implement Flutter MethodChannel scope payload, Android plugin bridge parsing, Python mirror refresh, MCP selector forwarding, or `list_changed`.
- Do not add automatic Navigator, RouteObserver, Android, or Flutter page lifecycle hooks.
- Do not add page-state top-level aggregation or a new scope-aware state endpoint.
- Do not change system route priority, auth bootstrap routes, SSE first frame format, or event frame shape outside the new scope-changed event payload.

### Selector Semantics

- A scoped lookup only starts when selector identity is complete: `X-DCP-Capability-Id` and `X-DCP-Capability-Scope` are present, and page scope also has `X-DCP-Page-Id`.
- Incomplete selector identity must not perform partial scoped lookup. It may fall back to legacy dispatch only if the implementation treats it exactly as absent; otherwise it must return a stable client error before leaking page existence. Auth still runs first.
- `registeredIds`, if retained, remains a legacy app-id/debug convenience view and must not be used as the scoped identity source.
