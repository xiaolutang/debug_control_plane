## Implementation Scope

### Goal

让 Flutter Dart 侧 `NativeControlPlaneBridge` 在 register/unregister/events/state/reverse-invoke 五条 MethodChannel 通路中原样保留 `scope/pageId/capId` identity（scope-aware local key 索引），且旧 app capability 调用路径零破坏。

### 关键决策

- **KD-1 scope-aware local key**：Dart 本地索引 key = `(scope, pageId?, capId)`，与 R003-BF005 Kotlin `ScopedCapabilityKey(scope, pageId?, capabilityId)` 逐字段同构——app key = `(app, null, id)`，page key = `(page, pageId, id)`。`_caps` 与 `_eventPumps` 升级为该 key；`_registeredIds` **不**升级（见 KD-2）。同一 scope-aware key 重复注册仍抛 `StateError`；app 与 page 同 capId、不同 pageId 同 capId 均允许共存。
- **KD-2 `_registeredIds` 保留 legacy 语义**：保持 legacy app-only debug 视图（与 R003-BF005 Selector Semantics 结论同构）——仅含 app capability id，不作为 scoped identity 源，scoped 查询只走 `_caps`。
- **KD-3 register API 兼容形态**：`Future<void> register(BridgeCapability cap, {CapabilityScope scope = const CapabilityScope.app()})`——scope 作为 bridge 层具名可选参数，缺省 app，旧调用签名语义不变；`BridgeCapability` 本身不持有 scope，inner capability 维持 BF002 `CapabilityScopeDefault` 语义。page scope 缺 `pageId` 时 Dart 侧拒绝（ArgumentError，native 侧拒绝属 FF002）。
- **KD-4 reverse invoke 兼容策略**：`capability.invoke`（native→Dart）payload 带 `scope/pageId` 时按 scope-aware local key 查 handler；payload 无 `scope` 字段的旧格式一律视为 app key 路由。key 未注册维持既有 `RouteFailure(404, not_registered)` 回填。
- `pageName` 不入 key，仅作展示元数据透传。

### 范围内

- `flutter_debug_control_plane/lib/src/bridge_capability.dart`：`BridgeCapability` 暴露注册时绑定的 inner scope（KD-3）。
- `flutter_debug_control_plane/lib/src/native_control_plane_bridge.dart`：
  - `register` 按 KD-3 签名扩展；page scope 缺 `pageId` 时 Dart 侧 `ArgumentError`，channel 不发消息。
  - `capability.register` payload 新增 `scope`、`pageId?`、`pageName?`。
  - `unregister` Dart 签名显式为 `Future<void> unregister(String id, {CapabilityScope? scope})`——`scope` 缺省 = app-only 删除，绝不误删同 capId 的 page capability（与 BF005 `legacy_unregister_app_only` 同构）；带 page scope 时按 scope-aware key 删除。
  - `events.emit`、`capability.state.update` payload 新增 `scope?`、`pageId?`。
  - reverse invoke 按 KD-4 查 handler。
  - `_caps`/`_eventPumps` 按 KD-1 升级为 scope-aware key；`_registeredIds` 按 KD-2 保持 app-only debug 视图。
- `flutter_debug_control_plane/test/native_control_plane_bridge_test.dart`：沿用 TestDefaultBinaryMessenger 捕获 outgoing `MethodCall` 的既有风格，新增/扩展场景：
  - register 默认 app：payload 含 `scope=app`、无 pageId。
  - register page scope：payload 含 `scope=page/pageId/pageName?`。
  - page scope 缺 pageId：Dart 侧参数错误，channel 不发消息。
  - app 与 page 同 capId 共存注册成功；不同 pageId 同 capId 共存注册成功；同一 scope-aware key 重复注册抛 `StateError`。
  - 旧签名 `unregister(id)` 只删 app 条目，page 同名条目保留；带 pageId 的 unregister 只删目标 key。
  - scoped unregister 后事件泵仅取消对应订阅，其它 app/page 订阅仍活跃。
  - events.emit / state.update payload 带 scope identity；app/page 同 capId 共存时 state.update payload 带 scope identity 可区分。
  - reverse invoke 带 scope 字段路由到对应 page handler；旧格式（无 scope 字段）路由到 app handler。
  - 未注册 scope-aware key 的 reverse invoke 保持既有 404 `not_registered` 回填。

### 已知约束

- `protocolVersion=1` 不变。
- 旧 payload（native→Dart 无 scope 字段）必须持续可路由——channel 兼容是 FF001 的 acceptance 项。

- `pageName` 仅展示元数据，不参与 key。
- pageId 校验由 `CapabilityScope.page()` 工厂承担（BF002 已交付），bridge 不重复实现——bridge 仅在注册入口处依赖工厂已保证的 pageId 非空不变量做防御性拒绝。
- channel 层字段命名须与 design §「Flutter MethodChannel payload」表逐字段对齐（`scope`/`pageId`/`pageName`/`capId`），Kotlin 侧对齐由 FF002 负责。
- `BridgeCapability.events` 单订阅契约（代码注释中的 D2）不变；scope 扩展不得改变事件泵语义。
- 过渡期安全：Android plugin 经 `call.argument` 逐键读取 payload，多余 `scope/pageId/pageName` key 被忽略，FF001 阶段 native 行为与旧 payload 完全一致；FF002 落地后开始消费。

### 任务流程图

```text
正常路径（page 注册）:
  Flutter 业务/FB001 helper → bridge.register(cap, scope: CapabilityScope.page(pageId, pageName?))
  → [Dart 校验] page 缺 pageId → ArgumentError（不发 channel；pageId 校验主体在 CapabilityScope.page 工厂）
  → capability.register payload {capId, resources, commands, scope, pageId?, pageName?}
  → [Android plugin parseDecl] 经 call.argument 逐键读取，FF001 阶段忽略新字段（行为与旧 payload 一致；FF002 开始消费）
  → 本地 _caps 记为 scope-aware key (KD-1)

正常路径（reverse invoke）:
  控制端 → native dispatch → capability.invoke {reqId, capId, routeKind, routeIndex, scope?, pageId?}
  → Dart 按 scope-aware key（scope 缺省 app，KD-4）查 _caps → handler(ctx)
  → capability.invoke.result 回填
异常: key 未注册 → RouteFailure(404, not_registered) 回填
异常: routeKind 未知 → RouteFailure(500, internal_error)（既有语义保持）

解除路径:
  旧 unregister(id) / unregister(id, scope: null) → 等价 app-only → 按 (app, id) 删，同 capId page 条目保留
  scoped unregister(id, scope: page(pageId)) → 只删该 key，事件泵仅取消对应订阅；其它 app/page capability 不受影响

事件/状态路径:
  events.emit / capability.state.update payload 追加 scope?/pageId?（缺省 app）
```
