## Implementation Scope

### Goal

Android plugin（`DebugControlPlaneFlutterPlugin` + `DartCapabilityRegistry` + `NativeControlPlaneBridge`）解析 FF001 Dart 侧发出的 scope-aware payload（scope/pageId/pageName），以三方同构的 scoped identity 索引 Dart 注册的 capability，unregister/events.emit/teardown 全链路按 scoped key 精确操作，且旧 app-only payload 行为零破坏。

### 关键决策

- **KD-1 scope-aware registry key（三方同构，三字段等值）**：`DartCapabilityRegistry.caps` 从 `LinkedHashMap<String, BridgeCapability>` 升级为 `LinkedHashMap<BridgeCapabilityIdentity, BridgeCapability>`，`data class BridgeCapabilityIdentity(val type: CapabilityScopeType, val pageId: String?, val capId: String)`——**仅这三字段参与等值/哈希**；完整 `CapabilityScope`（含 pageName 等）作为注册元数据保存于 `BridgeCapability.scope`，不作为 identity 等值来源（pageName 不入 key 由此结构性保证，消除「嵌整个 CapabilityScope」与「pageName 不入 key」的自相矛盾）。与 FF001 Dart `_ScopedCapabilityKey(scope, pageId?, capId)` 及 BF005 Kotlin core `ScopedCapabilityKey(scope, pageId?, capabilityId)` 逐字段同构：app key = `(app, null, id)`，page key = `(page, pageId, id)`。同一 scoped key 重复注册 → `IllegalArgumentException`（上游既有映射 `ERROR_DUPLICATE` 保持）；app 与 page 同 capId、不同 pageId 同 capId 共存。`registeredIds` 保持 legacy app-only debug 视图（与 FF001 KD-2 / BF005 Selector Semantics 同构），不作为 scoped identity 源。
- **KD-2 parseDecl 缺省语义 + page 缺 pageId 拒绝**：`parseDecl` 新增解析 `scope`（经 `CapabilityScopeType.fromWire`，未知值抛 IAE → `invalid_request`）；缺省 `app`（design「旧 payload 缺省 app」——旧 Dart 版本/手拼 channel 调用兼容）。`scope=page` 且 `pageId` 缺失/空白 → `IllegalArgumentException` → `invalid_request`（与 missing capId 同类；Dart 侧拒绝已由 FF001 交付，native 侧拒绝是 design 表的双侧要求）。`pageName` 可选、仅展示元数据透传，不入 key。`BridgeCapability` override `val scope: CapabilityScope` 携带注册时 scope，使 `ControlPlane.register(cap)` 经 `ScopedCapabilityKey.from(cap.scope, cap.id)` 派生正确 key（BF005 语义消费）。
- **KD-3 unregister/events.emit 的 scope 透传方案**：`CAPABILITY_UNREGISTER` 读取 `scope?/pageId?`（缺省 app-only），按 scoped key 查 registry，命中后调 `plane.unregisterScoped(scope, capId)`，绝不误删其它 page 同 capId 条目（与 FF001 Dart 端 app-only 缺省语义对称）。`EVENTS_EMIT` 读取 `scope?/pageId?`：显式携带时按 scoped key 找 event flow；**缺省语义与 FF001 Dart `_scopeFor` 同构**——按 capId 以 app 条目优先、回退查找首个已注册 key（两端一致，不允许字面「无条件缺省 app」造成 page-only capId 行为分叉；app 与 page 同 capId 共存时缺省路由 app 条目）。
- **KD-4 eventFlows/teardownCapability/pending invokes 的 key 升级（跨方法一致性）**：`NativeControlPlaneBridge.eventFlows` 从 `ConcurrentHashMap<String, MutableSharedFlow<DebugEvent>>` 升级为 `ConcurrentHashMap<BridgeCapabilityIdentity, ...>`；`eventFlow`/`registeredEventFlow`/`teardownCapability`/`invokeHandler`/`pullState` 签名统一改为携带 scoped identity（reverse-invoke 回调的 handler 定位与 Dart 端 FF001 scope-aware key 路由对齐）；`invokeHandler` 与 `pullState` 发出的 reverse invoke payload 均附 `scope`（page 时加 `pageId`），使 Dart 路由层可按 scope-aware key 定位 handler（FF001 KD-4 的 native 发端）。不升级会破坏 events.emit/unregister/teardown 三处 key 语义的一致性，故一并升级为方案而非局部补丁。`teardownCapability(identity)` 精确清理：只移除该 key 的 event flow、只 fail 该 capability 自己的 pending invokes（按 identity 过滤），不误杀其它 page。
- **KD-5 BF005 遗留测试修复（拾取，非本任务引入）**：`DartCapabilityRegistryTest` L127「events emit reaches the plane event bus with native sequence assignment」在干净 HEAD 上稳定失败——BF005 给 `ControlPlane.register` 加了 `capability_scope_changed` bus 事件，`transport.broadcasts.size == 1` 实际为 2（register scope_changed + tryEmit pressed）。BF005 未同步修 plugin 侧测试。本任务修复方式：断言按 event type 过滤（如 `broadcasts.filter { it.type == "pressed" }` 单例且 sequence 由 native 赋值），并在 contract 与 evidence 中显式记录这是拾取 BF005 遗留失败，不是 FF002 引入的回归。

### 评估者挑战记录

Round 1（evaluator perspective，`xlf-subagent:R003-FF002:contract-evaluator:01`）：

- **Q1（KD-1 key 等值字段）**：质疑——`BridgeCapabilityIdentity(scope: CapabilityScope, capId)` 嵌整个 `CapabilityScope`，而 `CapabilityScope` 是含 `pageName`/`revision` 的 data class，等值/哈希会把 pageName/revision 拼进身份，与「pageName 不入 key」约束自相矛盾，且破坏与 BF005 `ScopedCapabilityKey`（type+pageId+capabilityId）/FF001 `_ScopedCapabilityKey` 的逐字段同构（同 key 不同 pageName 重注册会绕过 duplicate 检测）。Round 2 处置——改为三字段 `BridgeCapabilityIdentity(type, pageId?, capId)` 等值/哈希，完整 `CapabilityScope` 降为注册元数据存于 `BridgeCapability.scope`。结构性消除矛盾，**已接受**。
- **Q2（events.emit 缺省语义跨端一致性）**：质疑——draft 的「缺省 app」与 FF001 Dart `_scopeFor`（app 条目优先、回退首个已注册 key）不同构：page-only capId 缺省 emit 在 native 会 not_started、在 Dart 会路由 page 条目，行为分叉。Round 2 处置——KD-3 改为与 `_scopeFor` 同构的 app 优先回退查找。**已接受**（非阻塞备注：任务流程图 L87 仍写「缺省 app」，以 KD-3 权威表述为准，实现时按 KD-3 执行；建议实现者在实现时同步该行措辞，不构成 needs_revision）。
- **Q3（文件越界 deviation 与测试落点）**：质疑——`NativeControlPlaneBridge.kt` 不在 tasks.md 文件清单，替代方案（plugin 层 scope→capId 映射、bridge 保持裸 capId）经核验不成立（app/page 同 capId 会命中同一 SharedFlow 串扰、teardown 按 capId 过滤误杀），延伸最小必要但 deviation 未闭环、teardown/pending-invoke 测试落点文件未声明。Round 2 处置——范围内显式登记 deviation 并由编排器确认 commit gate allowlist；`NativeControlPlaneBridgeTest.kt` 纳入测试范围。**已接受**。
- **Q4（reverse invoke scope 透传完整性）**：质疑——KD-4 只覆盖 `invokeHandler`，`pullState` 的 reverse invoke payload 未明确附 scope，page capability 的 state 拉取在 Dart 侧会按 app key 落空；且测试清单无 payload 含 scope/pageId 的桥层断言用例。Round 2 处置——KD-4 明确 `invokeHandler`/`pullState` 均附 scope（page 加 pageId），测试清单补两条桥层断言用例。**已接受**。

- **teardown no-op 语义**：unregister 目标 key 不存在 → no-op success（与 plane `unregisterScoped` no-op 语义一致），与 FF001 Dart 端 unregister 缺省行为对称——确认合理，无需修改。
- **BF005 遗留修复 evidence**：KD-5 要求 evidence 日志显示干净 HEAD 失败、修复后通过（编排器已确认干净树稳定失败）——修法（按 event type 过滤）最小正确，确认。
