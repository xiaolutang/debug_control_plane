## Implementation Scope

### 目标
在 example app 内交付授权 UI 控制层：`AcceptanceController`（ChangeNotifier 状态机）与授权弹窗 `AuthDialog`，把 BF006 `AcceptancePlane`/`AcceptanceDebugAuthManager` 的真实状态绑定到 FF002 已固化的 12 个稳定标识锚点上，完成 pending 弹窗 approve/deny、Controls 清 token/模拟过期、请求日志同步更新。

### 范围内
- 新建 `flutter_debug_control_plane/example/lib/src/acceptance_controller.dart`：
  - 定义 UI 层六态 `AcceptanceAuthState { idle, pending, approved, denied, expired, cleared }`（命名决策见约束）与 `AcceptancePlaneStatus { stopped, starting, running, failed }`；**复用** BF006 的 `AcceptanceRequestLogEntry`，不得重复定义。
  - `AcceptanceController extends ChangeNotifier`，持有 `AcceptancePlane`，暴露 `Future<void> approvePending()`、`Future<void> denyPending()`、`void clearToken()`、`void expireToken()`、启动 plane 的初始化方法，以及只读视图 `endpoint`、`authStatus`、`tokenPresent`、`requestLog`（含 route/statusCode/authResult 的追加记录）、`pendingRequestIds`、`activeClientLabel`、`activeRequestId`。
  - 订阅 `AcceptancePlane(onRequestLog: ...)` sink，将 `AcceptanceRequestLogEntry` 追加到请求日志并 notifyListeners。
  - 依据日志事件驱动 UI 状态：`/auth/request` 且 authResult==pending → authStatus=pending 并展示弹窗数据（clientLabel/requestId）；approve/deny/claim/cleared/expired 事件映射到 approved/denied/approved/cleared/expired。
- 新建 `flutter_debug_control_plane/example/lib/src/auth_dialog.dart`：
  - `AuthDialog` 组件复用 FF002 的 `_StableAnchor` 五个标识：`acceptance.auth_dialog.root/title/client_label/approve_button/deny_button`，绑定当前 pending 的 clientLabel/requestId 与 controller 的 approve/deny callbacks。
  - pending 弹窗出现时 approve/deny 按钮同时可见、不被键盘或系统栏遮挡（用 dialog/overlay 层级实现，非页面内嵌占位）。
- 修改 `flutter_debug_control_plane/example/lib/main.dart`（仅限接线，不改标识）：
  - `AcceptanceHomePage` 从 StatelessWidget 改为接收/controller 绑定形式（如 `AnimatedBuilder`/`ListenableBuilder`），将 Status 区域 endpoint/auth state/capability count、Requests 列表与 last result、Controls 按钮 onPressed 全部绑定到 controller。
  - 12 个稳定标识的 identifier 字符串与 `_StableAnchor` 结构不变（FF002 已固化）。
- 单测 `flutter_debug_control_plane/example/test/acceptance_controller_test.dart`（或并入现有 test 文件）：controller 状态机覆盖 pending/approved/denied/cleared/expired 五态流转 + 请求日志追加断言；widget 测试更新覆盖弹窗 pending 展示、approve/deny 点击、controls 点击。

### 已知约束
- **命名冲突决策**：BF006 已在 `acceptance_plane.dart` 定义 `enum AcceptanceAuthStatus { pending, approved, denied }`（wire 值枚举），与 tasks.md 片段中六态枚举同名。为避免重复定义和语义混淆，controller 的六态 UI 枚举命名为 `AcceptanceAuthState { idle, pending, approved, denied, expired, cleared }`，与 AcceptanceSpec `state.authStatus` 字段对应；controller 内部将 wire 状态映射到 UI 态。tasks.md 关键代码片段中的 `AcceptanceAuthStatus` 名称以此为准替换（语义不变）。
- 12 个稳定标识不可移除、不可改名（FF002 已固化）；`acceptance.auth_dialog.*` 从页面内嵌占位升级为真实 pending 弹窗时，必须复用同名 ValueKey+Semantics anchor。
- pending 弹窗可见时必须满足 `state.authStatus == "pending"`（AcceptanceSpec interaction_assertion #2）。
- expire 语义：点击 expire_token_button 后下一次敏感请求 authResult==token_expired（BF006 expireToken 将 expiresAt 置过去，由 authorize 拒绝路径产生日志）；controller 据此日志把 UI 态置为 expired。
- headless Flutter test 中启动真实 HttpServer（loopback port 0）是允许的（BF006 单测已验证此模式）；如个别环境不支持，测试可注入 fake plane/auth manager，但状态机断言不得删减。
- 状态单源：authState 文案、tokenPresent、request log 均从 controller 单一来源派生，禁止 UI 层本地缓存分叉。

### 任务流程图
App/test 启动 → controller.init() 调 plane.startDartPlane() → endpoint 写入 Status，planeRunning==true → 电脑端未授权敏感请求到达 → authManager.requestAuthorization→requestAuthorization 路由产生 pending 日志（含 clientLabel/requestId）→ onRequestLog sink → controller 追加日志并置 authStatus=pending → AuthDialog 弹出并绑定 client_label/requestId → 用户点 approve_button/deny_button → controller 转发 authManager.approvePending/denyPending → 日志回流（approved/denied）→ client claim 成功后 tokenPresent==true → Controls clear_token_button → tokenPresent==false（日志 authResult=cleared）；expire_token_button → 下次敏感请求日志 authResult==token_expired → UI 态 expired。

异常/降级：plane 启动失败 → AcceptancePlaneStatus.failed + endpoint 显示错误态，不崩溃；无 pending 请求时 AuthDialog 不显示；sink 回调在 notifyListeners 后异步调度（microtask）避免 build 期间 setState。
