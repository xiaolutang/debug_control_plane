## Implementation Scope

### 目标
为 example app 增加 Android 真机运行模式：新建 `AndroidNativePlane`（封装 `NativeControlPlaneBridge` 的 start/register/stop + pending auth 回调），并以最小改动方式将 `AcceptanceController` 从「强依赖 Dart `AcceptancePlane`」解耦为可运行于 Dart plane 或 native plane 两种模式，两种模式下同一 UI（12 标识）、同一 capabilityCount、同一 request log 语义可用。

### 已知约束
- **PlaneHost 是最小接口，不是重构**：只提取 controller 实际消费的 5 个操作（start/stop/capabilityCount/pending 通知/approve+deny），不得把 BF006 的 wire 协议类型泄漏进接口；`AcceptanceRequestLogEntry` 继续作为唯一日志类型（native 模式合成日志也产该类型）。
- **BridgeCapability 单订阅限制**：`events` 访问即占用，二次访问抛 StateError。BF006 的 `_AcceptanceCapability.events` 是 `const Stream.empty()`，Dart plane 的 HttpServer 从不消费 events，因此无冲突；但**同一 `BridgeCapability` 包装实例不得注册两次**——每次注册必须新建 `BridgeCapability(cap)` 包装。同一底层 `Capability` 实例（`buildCapabilities()` 每次 fresh 构建）不得同时在两个运行中的 plane 注册；模式切换需先 stop 再 start。
- **合成日志语义**：native 模式下 capability HTTP 请求日志在 Kotlin 侧，Dart 侧不可见。本任务约定：request log 条目 = 真实 HTTP 探测（integration 测试中对 endpoint 发起的请求）+ Dart 侧可观测的 auth 生命周期事件（pending/approved/denied/cleared 合成条目）。每条合成条目仍含 route/statusCode/authResult 三字段（route 取 `/auth/request` 等，statusCode 取 wire 语义值）。AcceptanceSpec interaction_assertion #7 在 native 模式下以 integration 测试真实请求的断言为准，UI 日志允许为 auth 生命周期合成条目——此语义放宽仅限 native 模式，Dart 模式断言不变。
- **capabilityCount 一致性**：native 模式注册 `buildCapabilities()` 的同一组 4 个 capability（echo/device-info/secure-action/error-case），capability_count_text 两模式恒为 4。
- expire_token_button 在 native 模式禁用是协商决策，评估不得因「native 模式 expire 不可用」判 FAIL；Dart 模式行为不变。
- 真机 integration 测试对 endpoint 的 HTTP 请求需真机与测试宿主网络互通（loopback 或局域网地址由 bridge 返回的 uri 决定）；若设备网络隔离导致不可达，按异常路径记 N/A 并回退 BF008 联调验证，不得伪造 PASS。
- 状态单源约束（FB001）延续：authState/tokenPresent/endpoint/requestLog 单一来源于 controller；native 合成日志也必须经 controller 单一入口追加。

### 任务流程图
正常路径（Android 真机）：main.dart 启动 → Platform.isAndroid → controller 绑定 native PlaneHost → AndroidNativePlane.start(bridge) → native Kotlin plane 绑定端口返回 Uri → endpoint 写入 Status、planeRunning==true → registerCapabilities(buildCapabilities() 包装为 BridgeCapability×4) → capabilityCount==4 → 电脑端/测试对 endpoint 发未授权敏感请求 → Kotlin PluginDebugAuth 挂起并经 channel 回调 Dart → DebugAuthRequest(requestId, clientLabel) → controller 置 authState=pending + 合成日志 pending 条目 → AuthDialog 弹出（复用 5 标识）→ 用户点 approve_button → bridge.approveAuthorization(requestId) → DebugAuthClaim → tokenPresent==true + 合成日志 approved 条目 → clear_token_button → bridge.revokeAuthorization(all:true) → tokenPresent==false + 合成日志 cleared 条目 → stop() → planeStatus==stopped。

正常路径（iOS simulator / Dart 模式）：Platform.isAndroid==false → DartPlaneHost 包装 AcceptancePlane → 行为与 FB001 完全一致（21 个既有测试零回归）。

异常/降级：bridge.start 抛 PlatformException(EADDRINUSE, errorCode=98) → planeStatus==failed + endpoint 错误态，不崩溃；pending 回调在 plane 已 stop 后到达 → 丢弃并记日志，不弹窗；双模式并发注册 → 禁止（先 stop 再切）；真机 HTTP 探测不可达 → integration 用例 FAIL 或记 N/A 回退 BF008，不伪造。

跨模块交互点：Dart↔Kotlin MethodChannel（kMethodChannel，协议常量 ChannelProtocol.kt，R001-FF003 已冻结，本任务只消费）。

### 评估者挑战记录
- Q1: controller 与 plane 解耦方式——提取接口还是 controller 加 mode 分支？
  A: 提取最小接口 PlaneHost（选项 a），但严格限定为 controller 实际消费的 5 个操作；AcceptancePlane 本体不改，用薄适配器包装。controller 内不出现 `if (mode == native)` 散布分支（模式差异封装在 host 实现内），以保护 FB001 state_consistency 单源约束。
  Conclusion: accepted。
- Q2: native 模式 request log 来源——HTTP 日志在 Kotlin 侧，Dart 侧只有 pending 回调，合成日志是否可接受？
  A: 可接受，但限定语义：合成条目仅覆盖 auth 生命周期（pending/approved/denied/cleared），每条含 route/statusCode/authResult 三字段；capability 级真实请求日志由 integration 测试进程对 endpoint 发起真实 HTTP 请求并在测试侧断言（满足 AcceptanceSpec #7）。UI 层不虚构 capability 调用日志。
  Conclusion: accepted。
- Q3: clear/expire token 在 native 模式（Kotlin PluginDebugAuth）下的语义？
  A: clear 映射 `revokeAuthorization(all: true)`（authResult=cleared、tokenPresent=false）；expire 无 native 等价 API，禁用按钮（不响应点击 + Semantics disabled），不改 Kotlin、不伪造 expired 流转。Dart 模式两按钮行为不变。
  Conclusion: accepted。
- Q4: capabilityCount 双模式一致性与 BridgeCapability 单订阅限制？
  A: 两模式均注册/构建同一组 4 个 capability（buildCapabilities() 每次新构实例，避免跨模式复用同一实例）；BridgeCapability 包装每次注册新建，规避 events 单订阅 StateError；BF006 capability events 为空流，与 Dart plane 无消费冲突。禁止两 plane 同时注册同一 capability 实例，切换必须先 stop。
  Conclusion: accepted。
- Q5: tasks.md 标记 deferred(device_required) 的 integration 测试本次改为实测是否合规？
  A: 合规。deferred 是设备未到位时的预案；真机 bc6763eb（23116PN5BC, Android 16）已连接，本次升级为实测：真机 integration（native plane 真实启动 + endpoint 真实 HTTP + pending 弹窗 approve）+ visual baseline 真机截图采集（撤销 deferred）。若实测时设备不可用，回退 deferred(device_required) 并在 evidence 记录，不得阻塞任务其余部分。
  Conclusion: accepted。
- Q6: iOS/Dart 路径零回归如何界定？
  A: FF002/FB001 既有全部测试（含 12 标识 widget 测试、状态机测试、6 用例 integration 夹具的 iOS 执行面）在本任务改动后全绿；main.dart 接线改动仅限模式选择注入，标识与 AuthDialog 不动。
  Conclusion: accepted。
- Q7: 本任务对「Python endpoint acceptance 调用」（AC#2）验证到哪一层？
  A: 归 BF005 联调。本任务验证到：native plane endpoint 真实 HTTP 可达（hello）、未授权敏感请求触发 pending、approve 后 claim/token 语义正确。Python runner 链路不在本任务 gates 内。
  Conclusion: accepted。
