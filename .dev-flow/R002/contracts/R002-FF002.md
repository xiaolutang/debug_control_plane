## Implementation Scope

### 目标
在 `flutter_debug_control_plane/example/` 交付可被 Flutter test 构建和检查的验收 App 骨架，提供 `main.dart`、`AcceptanceApp`、Status/Requests/Controls 三个 UI 区域，以及 AcceptanceSpec 12 个稳定标识的 Key/Semantics 锚点。

### 范围内
- 新建或补齐 `flutter_debug_control_plane/example/pubspec.yaml`，使用 path dependency 接入 `../` Flutter plugin 与 `../../dart` 的 `debug_control_plane`。
- 新建 `flutter_debug_control_plane/example/lib/main.dart`，提供 `void main() => runApp(const AcceptanceApp())` 和可测试的 `AcceptanceApp` 根组件。
- 在 App 首屏提供 Status、Requests、Controls 三个区域；手机竖屏下内容可滚动访问，文本不互相遮挡。
- Status 区域提供 endpoint、auth state、capability count 的占位/静态状态文本，可被后续 BF006/FB001 绑定真实状态。
- Requests 区域提供请求列表与 last result 的占位/空态结构，可被后续 BF006 request log sink 绑定。
- Controls 区域提供 clear token、expire token 控件锚点；本任务只保证按钮/锚点存在和可构建，不实现真实 token 清理/过期状态机。
- 落地 AcceptanceSpec 的 12 个 stable identifiers，优先同时使用 `ValueKey('<identifier>')` 与 `Semantics(identifier: '<identifier>')`；如当前 Flutter SDK 对 `Semantics.identifier` 不可用，必须保留同名 Key 并用 Semantics label/value 保证测试可定位。
- 为骨架补充 Flutter widget/unit test，验证 `AcceptanceApp` 可构建、三个区域存在、12 个稳定标识存在、占位控件点击不抛异常。
- Contract 固化 AcceptanceSpec 路径：`.dev-flow/R002/analysis/2026-08-24--flutter-auth-acceptance-app-acceptance-spec.yaml`。

### 范围外
- 不实现 R002-FB001 的真实授权弹窗状态机、同意/拒绝控制、pending/approved/denied/cleared/expired 状态流转。
- 不要求本任务完成 `/auth/request/status/claim` 的 UI 交互绑定；该链路由 R002-FB001、R002-BF005 和 R002-BF008 接续。
- 不实现 Android native bridge，不新增 Kotlin/Android native 侧代码。
- 不实现 iOS native plugin bridge；iOS 模拟器真实 plane 验收继续走 Dart plane。
- 不实现 Python acceptance runner 或 shell endpoint 验收脚本。
- 不引入产品业务页面、业务依赖或复杂 showcase 视觉设计。
- 不修改 R001 鉴权协议、token 生成/校验逻辑或 MCP adapter 架构。

### 已知约束
- `debug_control_plane` 是多产品复用基础设施，example app 只能作为验收夹具，不得 import 业务包。
- 架构事实边界在 App debug plane；本任务只提供 Flutter UI 宿主锚点，不能把授权判定迁移到 Python adapter。
- R002 第一阶段验收目标是 iOS simulator + Flutter app + Dart plane；Android 真机 native bridge 后续接入。
- visual baseline 因需要模拟器/真机运行环境可 deferred，`deferred_reason=device_required`；但 visual-verify 仍必须对结构、状态、视觉三层证据给出 PASS，不能以 deferred 跳过。
- 本任务的状态文案和控件行为是占位结构，后续 FB001 接入时必须保持 stable identifiers 不变。

### 任务流程图
Flutter test 或用户启动 example app → `main()` 创建 `AcceptanceApp` → 构建根 Material/Cupertino 宿主 → 页面渲染 Status、Requests、Controls 三个区域 → 每个区域挂载对应 Key/Semantics stable identifiers → Flutter widget test 查找 identifier 并验证组件存在。

后续接入路径：BF006 Dart plane 提供 endpoint/capability/log sink → FB001 controller 将 plane/auth/request 状态绑定到 FF002 的 Status/Requests/Controls anchors → BF005/Python runner 触发真实 MCP/debug plane 请求 → UI 通过同一 stable identifiers 展示 endpoint、auth state、request log 和 controls 状态。

异常/降级：Flutter SDK 不支持 `Semantics.identifier` 时 → 使用同名 `ValueKey` 作为主定位载体，并以 Semantics label/value 辅助可访问性定位 → widget test 仍必须证明 12 个逻辑标识逐个可定位。真实设备不可用时 → visual baseline 截图记录为 deferred/device_required → visual-verify 仍检查 widget tree 结构、状态文本和无截断/无遮挡的运行截图或测试渲染证据。

### 评估者挑战记录
- Q: FF002 是否应该实现真实授权弹窗和 approve/deny 状态机，才能让 auth dialog identifiers 通过？
  A: 不应该。FB001 才负责真实授权弹窗状态机；FF002 只需提供可被后续接入的 UI anchors/占位结构，包括 dialog root/title/client/approve/deny 的稳定标识载体。
  Conclusion: accepted。evaluate 检查 anchors 和占位结构，不要求真实 pending 请求驱动弹窗状态机。
- Q: visual baseline deferred 是否意味着可以跳过 `visual_check_passed`？
  A: 不可以。baseline 截图因 device_required 可 deferred，但 visual-verify 必须基于 AcceptanceSpec 的视觉断言提供结构、状态、视觉三层 PASS 证据；缺证据则本任务 FAIL/UNCERTAIN。
  Conclusion: accepted。contract 将 baseline deferred 与 visual-verify PASS 分开约束。
- Q: 是否可以只用普通文本而不落 Flutter Key/Semantics？
  A: 不可以。R002 验收依赖 stable identifiers 作为跨自动化和人工检查锚点；12 个标识必须逐个落地到 Key/Semantics。
  Conclusion: accepted。`stable_identifiers_present` 为 UI hard gate。
